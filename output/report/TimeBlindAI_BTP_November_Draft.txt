Abstract

TimeBlindAI is a web-based productivity assistant for task duration estimation, task decomposition, scheduling, focus sessions and review of recorded outcomes. The previous semester established the conceptual Intelligent Time Orchestration System architecture and a responsive interface. The present phase implements a FastAPI backend, a Next.js frontend, authenticated workspaces, task and session persistence, adaptive scheduling rules, optional Windows activity collection, and administrator exports.

The system combines deterministic temporal reasoning with an optional pretrained language-model integration. Generated task plans and schedule-order proposals are checked by application logic, while a rules fallback supports operation when an external provider is unavailable. This integration is API inference rather than training a language model. Earlier small-scale duration checks did not establish that the model improved on the rules baseline.

An exploratory participant pilot uses the original application through a guided study entry point. Participants receive genuine LLM task plans, use the original focus workspace and create saved AI-assisted schedules. Their own guesses and an independent rules baseline are retained before work starts. Each attempted task records its timing source, scope status and a short plan review. A separate scheduler review asks about feasibility, ordering and guidance. Human outcome results remain pending.

1 Introduction

Planning a task requires a prediction about the time needed to finish it. When that prediction is inaccurate, a schedule can become difficult to follow even if the task list itself is clear. TimeBlindAI addresses this practical problem by connecting the initial plan to recorded execution and subsequent feedback in one application.

The project originated as an Intelligent Time Orchestration System, intended to combine sensing, temporal reasoning, personalization and interventions. Last semester's report concentrated on the conceptual ontology and architectural domains, with a responsive frontend as the initial implementation. This phase develops a working software path through task creation, decomposition, scheduling, timed work and outcome review.

This report separates three types of contribution. The first is engineering: an authenticated web application with persistent task and session records. The second is algorithmic integration: rule-based estimates and scheduling together with an optional language-model interface. The third is evaluation: reproducible synthetic checks and a prospective participant pilot. A functioning feature is not itself evidence that it improves a user's productivity; that distinction determines the evaluation design.

1 1 Scope of the current phase

The implemented system assists with planning and collects operational records. The participant study focuses on the usability of this workflow and on agreement between predicted and recorded task durations. It does not diagnose a condition, infer verified cognitive load, or establish that notifications improve attention. Clinical benefits and long-term behavior change are outside the current evaluation.

1 2 Progress since the previous semester

The conceptual domains are now represented by application modules and database entities. Tasks, events, sessions, schedule blocks and interventions have concrete records. A Windows companion provides optional foreground-application and inactivity observations. A study-specific entry point adds explicit pilot consent and immutable prediction snapshots. These changes make prospective evaluation possible while retaining the broader architecture as a direction for future development.

3 Problem Statement and Objectives

The engineering problem is to connect a user's task intention to a feasible plan and an interpretable record of what happened. The evaluation problem is to measure this workflow without treating generated advice, synthetic behavior or retrospective guesses as observed evidence of human improvement.

The current objectives are to implement authenticated end-to-end task planning and session recording; maintain a deterministic scheduling and fallback path; expose optional generative planning with provenance; collect prospective paired estimates and timed outcomes; and document usability problems and evidence limits.

3 1 Evaluation boundaries

Approximately twenty participants and sixty task attempts are recruitment targets. The study is not powered to demonstrate a clinical outcome or a causal increase in productivity. An initial usability pilot remains useful if fewer people finish; the report must show recruitment and attrition rather than substitute planned counts for observed ones.

4 Architecture and Ontology Mapping

The application uses a Next.js and React frontend with a FastAPI backend. SQLAlchemy provides persistent domain records, using SQLite by default and supporting a configured PostgreSQL deployment. The frontend proxies API requests to the backend, allowing the browser to use the same origin for authenticated requests. Server-side ownership checks restrict access to each user's workspace.

The ontology remains a conceptual description of the domain. In this implementation, it is reflected in typed schemas, database relationships and module boundaries. The presence of entities such as attention state does not establish a validated latent-state estimator. A separate formal ontology reasoner is not claimed by this report.

4 1 Data flow

After authentication and study enrollment, participants explicitly confirm the AI data-use information. Task descriptions and limited completed-task history may reach the configured provider; optional desktop activity is not included in these planning prompts. Plans and steps are saved as ordinary tasks. Starting work creates a shared session that the original focus workspace can resume. Its pilot completion action returns to the guided outcome and review form, preserving one timer and one study record.

5 Implementation

The main application provides user registration and password login, authenticated workspaces, task decomposition, event preparation, scheduling, focus sessions, post-session feedback and review insights. Administrator routes require an explicit grant, and exported operational datasets omit credential tables. The newest participant flow builds on these foundations rather than introducing a separate data collection service.

5 1 Duration estimation and generative planning

The deterministic decomposer supplies a comparison baseline from task characteristics. The main app supports historical adjustments and optional pretrained-model calls. In the guided AI pilot the latter is required for new plans: estimates, steps, assumptions and explanations are returned by the provider and validated by the backend. Structured output validation does not prove duration accuracy.

The guided AI pilot requires a successful LLM response for each new task plan and saved schedule. It uses the same task estimator and scheduling route as the main application. Python still checks output structure and places feasible blocks. AI outages produce a visible failure, not a rules plan presented as AI. An independent unpersonalized rules estimate remains a comparator, and provider/model/prompt provenance is saved.

5 2 Scheduling and interventions

Schedules place work around time windows, events and dependencies, using a greedy heuristic with risk buffers. Replanning retains relevant ongoing and completed work and records revisions. Reminders respond to programmed signals including overdue work, switching bursts and observed inactivity. These are operational proxies. Idle input can reflect reading or thinking, and switching applications can be relevant work.

The previous report's estimate-relative deviation is actual duration minus estimate, divided by estimate. The live overdue reminder policy uses minutes past a block's end divided by planned duration. The two ratios refer to different events and must not be presented as the same measure or as a clinical timeblindness score.

5 3 Study collection and administration

The /study page contains participant information, consent, task entry, timing and final feedback. The /study/admin page displays counts and paired error summaries. Study tables store enrollment, prediction and outcome snapshots, and feedback. Withdrawn participation is excluded from the dedicated study summary, comments and export. The raw operational database remains private until deletion by the project team.

6 Evaluation Methodology

We propose a short prospective pilot with approximately twenty adult volunteers recruited through the project team's peers. Each participant is asked to attempt three naturally occurring tasks over two days. Two separate practice accounts should first exercise the entire hosted workflow and then be withdrawn from analysis. Recruitment is a convenience sample, and no random assignment or clinical screening is planned.

6 1 Task procedure

For duration evaluation, participants select unstarted work with a clear completion condition. The application records the initial guess, independent rules estimate and AI plan before revealing the result. Participants use the original focus workspace or its shared study timer, then return to the guided form to report breaks, completion, scope changes and per-task feedback. Recalled or hypothetical manual values support a quick interface rehearsal but are excluded from prospective accuracy.

The target task scope is usually fifteen to sixty minutes, with longer work divided into concrete units. The study does not require participants to manufacture tasks to reach a quota. Participants who stop early can still provide feedback after an attempted task. The app estimate is visible during use and may influence pace; the resulting comparison is therefore not blinded.

6 2 Outcomes and exclusions

Recorded work time equals server elapsed time minus self-reported breaks. A task enters the paired accuracy analysis only if the participant still consents, the task was completed, scope did not change and recorded work time is at least one minute. Scope changes, unfinished attempts and missing outcomes are counted separately. Both prediction methods use exactly the same eligible rows.

Primary descriptive accuracy is mean absolute error in minutes. We also report median absolute error and the percentage of tasks whose error is at most fifteen minutes. To avoid allowing participants with more records to dominate the summary, we compute each participant's mean error and average these participant means. The number of participants is reported separately from the number of tasks.

6 3 Feedback and safeguards

Five custom agreement questions measure ease, clarity, usefulness, trust and willingness to use the app again. Each item's median and five-category distribution are reported separately. These items are not the System Usability Scale and are not converted to a standardized score. Optional comments are coded into descriptive themes after removal of identifying information.

8 Discussion and Limitations

The implemented system makes planning decisions and their recorded outcomes observable within a connected workflow. This is the principal engineering advance over the previous semester's conceptual architecture. The participant pilot is intended to reveal whether users can complete that workflow and whether the estimates are useful enough to justify further refinement.

Interpretation is limited by convenience sampling, a short collection window, task diversity and repeated observations from the same people. Friends of the project team may provide more favorable feedback. Participants choose their own tasks, and scope can be difficult to express consistently. Break durations are self-reported; the server clock does not distinguish focused work from unrelated activity. A visible prediction may influence the outcome it is compared with.

The pilot now compares AI estimates against human guesses and independent rules where matching live outcomes exist. Historical rules-only pilot records remain separate. A guided path through the actual task and scheduling APIs replaces the earlier hypothetical scheduler exercise. There is still no randomized condition establishing causal productivity gains, clinical benefit or long-term personalization.

Prior offline modeling also requires caution. Features such as the number of sessions eventually completed for a target task are unavailable when that task is first predicted. Such post-task features cannot support a prospective accuracy claim. New comparisons should use only information available before work starts, maintain a frozen evaluation set and keep synthetic data separate from consented human records.

8 1 Interpretation after collection

The final discussion should explain the direction and variation of observed errors, which parts of the workflow participants found difficult, and which changes the evidence supports. If rules estimates are worse than human estimates, that remains a useful result: it identifies the need for better task-scope inputs and future calibration. A small or inconclusive pilot should lead to a restrained conclusion rather than an invented improvement percentage.

9 Future Work

The immediate next step after the pilot is to address recurring usability and reliability problems identified by participants. Changes to consent or timing should be distinguished from changes to prediction behavior, and a new protocol version should be used for a materially different experiment.

A larger prospective dataset could support calibration using historical tasks completed before each new prediction. Evaluation should preserve participant grouping and time order, and avoid training on the same tasks used to report performance. Task-scope descriptions and quantity units deserve particular attention because a task category alone cannot determine a person's workload.

The optional language-model method requires a separate paired evaluation with provider failure rates, successful-call accuracy and full-policy accuracy including fallback. Schedule quality should be tested under identical task durations, windows, events and dependencies, with explicit hard-constraint checks. Reminder benefit would require a comparison design that measures outcomes beyond whether a programmed rule fired.

Longer-term work can study sustained use, participant control over reminders, deployment reliability and more accessible interactions. Clinical claims would require a different evaluation scope and appropriate expertise. The current engineering system provides a platform for such work, while the November pilot remains a limited first observation of everyday use.

10 Conclusion

TimeBlindAI has progressed from a conceptual Intelligent Time Orchestration System and responsive interface to an integrated application with authenticated task planning, scheduling, sessions, feedback, optional activity monitoring and administrator data access. Deterministic logic supplies a verifiable baseline, while optional generative planning extends the system without establishing superior predictive accuracy.

The November evaluation design connects prospective human, independent rules and AI estimates to recorded outcomes and custom usability feedback. Separate study snapshots, consent filtering and explicit eligibility rules support an auditable analysis. These mechanisms address the need for measurable evidence without confusing synthetic checks with participant outcomes.

Appendix C Data Model and API Design

The persistent model separates planned work from recorded execution. A user owns tasks, events, schedules and sessions. Task steps belong to a task and carry their order and suggested duration. Dependencies express prerequisites between tasks. A schedule groups time blocks for a date, and blocks can refer to tasks or reserved events. A session can be linked to both a task and a block, allowing planned and observed timing to be compared.

This separation matters when a plan changes. A task is a description of work; a time block is an allocation; a session is an observation of execution. Treating them as the same object would make it difficult to distinguish an inaccurate estimate from a late start or a rescheduled commitment. Plan revisions preserve changes instead of replacing every earlier state without an audit trail.

C 1 Request validation and resource ownership

Pydantic schemas validate structured requests, including supported task types, difficulty values and numeric limits. Workspace authorization checks resource references against the authenticated user before operations proceed. Study routes derive the enrollment from the logged-in user and resolve each study record through that enrollment. Administrator operations require an explicit grant rather than relying on a hidden page or an email string displayed in the interface.

Task creation and decomposition are distinct operations in the main application. Decomposition proposes a plan; creation persists the task, and step endpoints save the generated steps. The study path saves its own independent estimate snapshot together with the ordinary task and steps. It does not trust a client-supplied rules prediction or accept a client-supplied completion timestamp.

C 2 Study state transitions

A study task begins in planned state. Starting it records server time and creates a linked session, moving it to active state. A finished record becomes completed or unfinished. Predictions cannot be patched through the study API, and a second finish request is rejected. A database constraint permits only one active study task per enrollment. This reduces overlapping timers and protects against accidental duplicate starts.

Enrollment retains its protocol and withdrawal timestamp. Withdrawal excludes records from study analysis; deletion requires separate removal of private records and working copies.

Appendix D Reasoning and Scheduling Details

The rules decomposer uses a base duration by task category, difficulty multipliers and task-specific quantity rules. Text keywords also help select an interpretation. The category baselines in the inspected code include 60 minutes for assignments, 35 for reading, 50 for study, 55 for writing and 65 for coding. Easy, medium and hard difficulty use multipliers of 0.85, 1.0 and 1.25. These are programmed defaults, not parameters learned from the November participant cohort.

Category defaults and historical calibration remain deterministic comparison mechanisms. New guided plans require successful LLM output. The independent rules comparator omits the personal guess, while AI receives task scope and limited historical outcomes. Separate method labels prevent older rules records from being mistaken for AI results.

D 1 Feasibility and task decomposition

The decomposer returns a total estimate, steps, confidence label, urgency and a fit assessment where applicable. The fit assessment compares available time with predicted work. It can report that a task fits, is tight or overflows the available window. An approaching deadline does not justify reducing the required work solely to make the calendar look feasible.

Steps make a high-level goal easier to act on, but their proposed minutes are still estimates. The system should communicate assumptions and allow task scope to be clarified. A confidence label from rules is a heuristic communication device; it is not a measured probability that the task will finish within the proposed time.

D 2 Generative inference and validation

The optional provider receives task details and a bounded selection of historical examples. It is asked to return structured predictions, steps and explanations. The backend validates schema and cross-field consistency, including duration ranges and step sums. A valid JSON response can still be inaccurate, so formatting reliability and predictive accuracy are evaluated separately.

For schedule generation, the language model may propose task ordering. Python retains responsibility for calendar placement and constraint checks. External inference can fail through network errors, exhausted provider quota, invalid structure or inconsistent outputs. The application records provenance and can return a rules fallback. A fallback is not counted as a successful language-model response in evaluation.

D 3 Adaptive replanning

The scheduling logic considers deadlines, priority, task duration, dependencies, fixed events and available time. It selects feasible work with a greedy procedure and records tasks that cannot fit. An active session reserves forecast completion time rather than being ignored when the remaining day is replanned. Updated remaining-time reports allow the forecast to change while preserving ongoing work.

Policy evaluation is limited to at most once every thirty seconds per user while the application or companion is operating. Replanning can respond to task changes, reservations, remaining-time updates and time progression. This behavior is a heuristic adaptation mechanism; the repository does not establish that it finds a globally optimal schedule or improves completion rates for users.

D 4 Intervention rules

The documented initial policy prioritizes slippage, late starts, switching, idle observations and upcoming work in that order. Slippage prompts require at least five overdue minutes and an overdue-to-planned-duration ratio of at least 0.20. A sustained-switch signal requires sufficient recent coverage and sustained active runs; a burst of four switches within five minutes can trigger the switching rule. The input-idle rule requires at least 120 observed idle seconds. Ten-minute global cooldowns reduce repeated prompts, with a longer twenty-minute interval for minimal reminders.

These thresholds encode the design's starting behavior and should be reported as configuration rather than empirical discoveries. Observations must be fresh; missing observation time is not treated as idle time. The participant pilot does not experimentally isolate these reminders, and their presence cannot support an effectiveness claim.

Appendix E Authentication Monitoring and Deployment

The application stores salted password hashes using PBKDF2 with SHA-256 and 600,000 iterations. Login uses opaque session tokens whose hashes are stored server-side. Cookies are HTTP-only, use SameSite protection and become Secure in the configured production environment. Authentication has rate limiting, and browser mutations require a request-protection header with origin checking. These mechanisms reduce specific access risks; they do not constitute an independent security audit.

The account recovery mechanism is an operator capability. A universal recovery key can reset accounts, so it must remain private and must never be included in the report, repository or participant materials. Account emails, passwords, cookies, pairing tokens and private provider keys are omitted from this draft and from research exports.

E 1 What Windows monitoring measures

The optional Windows companion samples foreground application and input inactivity approximately every two seconds. It sends executable basenames and bounded timestamp intervals. Full executable paths are discarded locally. After sixty seconds without input, new observations are classified as idle. Suspend gaps and unavailable processes are handled as missing or unknown observations rather than confidently labeled behavior.

Browser tabs share one executable identity, as do windows of the same application. Very short switches can be missed. Reading and thinking can create input inactivity. The companion therefore measures device interaction patterns, not ground-truth distraction, cognitive load or task progress. Pairing tokens are scoped to a session, stored as hashes and revoked when collection ends. Monitoring is optional and not required in the November pilot.

E 2 Deployment requirements

The existing deployment uses separate frontend and backend services. Both should run the same reviewed source revision. Frontend API rewrites depend on the configured backend URL at build time. The backend requires its persistent database URL and the allowed frontend origin. Local build success establishes that the source can compile; it does not establish that these hosted settings or account grants are correct.

SQLite on an ephemeral filesystem can lose records during service restarts or redeployment. The pilot requires either an existing persistent database service or a correctly mounted persistent disk. If both authors code responses, describe how disagreements were reconciled rather than assuming agreement.

A negative result should explain the failure pattern and its implications. If estimates are consistently too short, task scope or category defaults may need revision. If users appreciate decomposition but distrust durations, discuss those outcomes separately. If participation is low, report feasibility and barriers without claiming the planned sample was achieved. No inferential significance or productivity improvement is assumed in advance.

Appendix I Guided AI Pilot Revision

The revised workflow is a guided study mode for the original application. It does not substitute a generic scheduler for the project implementation. AI task plans are persisted as ordinary tasks and steps. The original focus workspace resumes the same active session; pilot completion returns to the task review form. The scheduling exercise now creates actual upcoming tasks and calls the original schedule generation route with AI required. Participants can open scheduled focus blocks directly and review the saved plan afterwards.

AI-assisted scheduling is a hybrid implementation. A pretrained LLM proposes task order and explains its ordering; Python places work and enforces time windows, deadlines, dependencies, events and breaks. This is not model training or an unconstrained LLM calendar. The application does not return a rules schedule as a successful AI trial if the provider is disabled or unavailable.

I 1 Scope changes and per task reviews

Scope means the amount and finish condition of the work being estimated. Estimating five pages but completing ten changes scope. Taking longer to complete the original five pages does not. Scope-changed tasks are retained in the participation accounting and excluded from paired duration error. Every guided task's completion form asks whether the plan helped and whether the estimate seemed reasonable, using separate five-point ratings, alongside friction and optional written comments.

Three timing modes are explicit: live timer, recalled real duration and hypothetical rehearsal. Neither manual mode enters primary prospective duration accuracy. Rehearsal values do not become ordinary task duration-training targets. Real accuracy still requires doing real work; allowing immediate manual entry cannot create a measured human outcome.

I 2 Current integration evidence

A live Groq scheduler ordering request using isolated synthetic inputs returned a valid LLM ordering. An initial task request failed provider-side JSON validation because the generated response exceeded the permitted step count. The task prompt was revised to prefer three to six useful steps, cap the count at twelve and check duration consistency. A subsequent live request to openai/gpt-oss-120b returned a 45-minute plan with five steps whose durations summed correctly. The revised task prompt is timeblind-v2.

These are local integration observations, not participant results or a reliability-rate estimate. The initial failure must not be erased from the account of the check. Controlled regression tests use mocked provider output and cannot establish live provider accuracy. Render configuration and a complete hosted participant journey remain to be verified after deployment.

I 3 Measures and interpretation

Task accuracy uses prospective completed tasks with unchanged scope and valid live timing. Report human and rules results on their eligible cohort, and AI results with its explicit successful-plan sample size. The report-safe export records AI estimate values, model and prompt identifiers, per-task rating values and AI-attempt success/failure. Free text and task descriptions are omitted from that export.

Scheduler constraint conformance is the percentage of saved plans passing the specified checks. Perceived usefulness is the share of reviews rating guidance four or five, with numerator and denominator. Recorded schedule adherence compares completed nonmanual blocks with their planned end times; original snapshots remain distinguishable from later schedule revisions. Manual-duration sessions are labeled and excluded from that execution measure. Hypothetical inspection alone does not supply adherence evidence.

The admin summary separately reports planned task blocks, completed nonmanual blocks, completion by planned end, manual exclusions and missing or replaced blocks. Missing execution must not be counted as a successful completion or hidden by reporting only those who finished. These records depend on participants honestly starting and ending sessions; they do not independently verify attention.

I 4 Deployment and remaining evidence

Configure the Render backend with persistent DATABASE_URL, LLM_ENABLED=true, the selected LLM_PROVIDER and LLM_MODEL, a private provider key, and LLM_FAILURE_MODE=error for the AI pilot. Keep provider secrets on the backend. Restart or redeploy both services from the same source revision and verify a complete hosted journey before invitations. Existing participants must confirm the updated AI data-use information before new study provider calls.

No participant sample, accuracy percentage or productivity benefit is manufactured in this draft. The final report requires the observed cohort and dates, provider attempts and failures, valid paired durations, per-task ratings, scheduler reviews and any measured execution. It also requires verified author contributions, current interface screenshots, final reference checks and actual signatures.
